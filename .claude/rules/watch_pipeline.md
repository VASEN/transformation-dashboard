# watch_pipeline.sh — справочник

Вынесено из CLAUDE.md 03.09.2026 (path-scoped: грузится при работе с этими файлами).

## Автопрогон по свежей выгрузке (`watch_pipeline.sh`)

Выгрузку из Redmine достаточно **положить в корень проекта** — остальное происходит само.
Триггер — LaunchAgent `com.vz.transformation-pipeline` с `WatchPaths` на папку проекта;
он будит `watch_pipeline.sh` на любое изменение папки, а решение «работать или выйти»
скрипт принимает сам.

Что делает прогон:
1. переименовывает выгрузку в `issues_ДД.ММ.xlsx` по **сегодняшней дате**;
2. `./deploy.sh <файл>` — `extract_data.py` → `overdue_report.py` → коммит `data.json` → пуш;
3. `upcoming_report.py --to <пятница>` — справка по срокам от сегодня до конца недели.

**Повторный заброс в тот же день** проходит цикл заново: файл дня перезаписывается молча,
данные пересчитываются. Так вечерняя картина замещает утреннюю (задачи, закрытые за день).

**Еженедельная telegram-сводка здесь не собирается.** `deploy.sh` вызывается без `$2`,
поэтому `process_report.py` не запускается: он читает `ОТЧЕТ_ДД.ММ.md`, и автопрогон
в середине недели собрал бы сводку по прошлонедельному отчёту. Сводку по-прежнему делает
владелец — `./deploy.sh issues_ДД.ММ.xlsx ОТЧЕТ_ДД.ММ.md ОТЧЕТ_предыдущий.md`.

### Почему прогон не зацикливается

Пайплайн сам пишет в ту же папку (`data.json`, `overdue_tasks_*.txt`, справки) — каждая
запись снова будит launchd. Три предохранителя:

| Предохранитель | Что закрывает |
|----------------|---------------|
| Замок `logs/.lock` (каталог + PID внутри) | наложение прогонов. Снимается только замок **мёртвого** процесса (`kill -0`): застрявший на 40 минут `git push` жив, и отбирать у него замок нельзя. `trap` удаляет замок, только если он всё ещё свой |
| Отпечаток `logs/.processed` — `<статус> <mtime\|размер> <pid>`, пишется **до** работы | собственные записи скрипта — и повтор упавшего прогона. `started` → работа идёт, `done`/`failed` → попытка завершена, повтор только по `--force`. Иначе падение `deploy.sh` уводило бы скрипт в бесконечный цикл коммитов, пушей и сообщений об ошибке |
| Статус `started` + **мёртвый** pid = оборванный прогон | launchd шлёт SIGTERM при выходе из системы, и убитый на середине прогон без статуса выглядел бы обработанным: выгрузка молча пропала бы, а `data.json` остался вчерашним. Такой прогон повторяется, и в итоговом сообщении появляется строка «↻ прошлый прогон был оборван» |
| «Только сегодняшняя выгрузка» (mtime ≥ начала дня) | посторонний будильник от правки кода не переименует вчерашний файл в сегодняшний |
| Дата в имени = сегодня | старый снимок, вернувшийся в корень (`cp archive/issues/…` даёт свежий mtime), не уедет на дашборд как актуальные данные |
| Проверка колонок Redmine **до** `mv` | `mv -f` затирает снимок дня безвозвратно (выгрузки в git не хранятся), а маска `issues*.xlsx` ловит любой файл на «issues». Требования те же, что у пайплайна — `extract_data.validate_source_columns` |
| Замок берётся максимум за три попытки | `mkdir` может не выполняться и не из-за чужого замка (каталог недоступен, нет места). Бесконечный цикл занял бы метку агента навсегда: launchd не поднимет второй экземпляр, и автопрогон встанет молча |

**Проверка различает два исхода.** Код возврата `2` — файл действительно чужой
(нет обязательных колонок): выгрузка помечается обработанной, уходит сообщение.
Код `3` — проверку **не удалось выполнить** (рассинхрон numpy/pandas, недоступный
файл): отпечаток НЕ пишется, потому что диагноз неизвестен, и после починки среды
выгрузка подхватится сама. Сообщение в этом случае гасится через `logs/.skipped`.

**Отбракованный файл не пропадает молча.** Если выгрузка не прошла проверку по дате
или по колонкам, об этом уходит сообщение с подсказкой `--force`, а её отпечаток
запоминается в `logs/.skipped`, чтобы не повторять это на каждое пробуждение
(их порядка шести в минуту). Причина: файл, скачанный вечером и перенесённый в папку
утром, сохраняет старый mtime — а тишину владелец читает как «всё прошло».


Кандидат — самый свежий по mtime файл `issues*.xlsx` в корне (`issues.xlsx`,
`issues (1).xlsx` — как скачалось). Перед работой скрипт ждёт, пока размер файла
перестанет меняться (докачка браузером), максимум ~10 с.

### Часовой пояс

Даты берутся по `TZ=Europe/Moscow`: машина стоит в `America/New_York`, а выгрузка
приходит утром по Москве — по локальному времени она получила бы вчерашнее число.
Тот же пояс у соседнего агента `LIFE/bin/redmine_watch.py`, иначе имена снимков
`issues_ДД.ММ.xlsx` разъехались бы между ними. Оба агента висят на одной папке и не
мешают друг другу: наш нормализует имя, которого тот ждёт.

### Итог прогона: Telegram + всплывашка + лог

Каждый прогон заканчивается **сообщением в Telegram** — владелец не должен заглядывать
в папку, чтобы понять, закончилась работа или нет. Канал тот же, что у
`LIFE/bin/redmine_watch.py`: `python3 ~/Projects/LIFE/bin/tg.py "текст"` (токен в keychain
`vz-telegram-bot`, chat_id в `shared/telegram/state.json`). Недоставленное сообщение
прогон не роняет — пишется предупреждение в лог.

Успешный прогон — файл, цифры из свежего `data.json` (проекты/задачи/просрочки/%
высвобождения), сводка справки с именем файла и статус пуша. Цифры важны: «готово»
без них не отвечает на вопрос, та ли выгрузка обработана.

**Сбой** уходит отдельным сообщением: шаг, код возврата, хвост лога **текущего прогона**
(`log_tail` режет по маркеру `─── новая выгрузка`, иначе затекает история прошлых),
команда повтора `./watch_pipeline.sh --force` и путь к полному логу. Функция `fail`
зовётся перед каждым аварийным выходом — тишина в Telegram никогда не означает
«прогон прошёл».

Исходы `deploy.sh` разведены по трём сообщениям:

| Исход | Заголовок | Что дальше |
|-------|-----------|-----------|
| успех / «данные не изменились» | `✅ Дашборд обновлён` | справка собирается, прогон завершён |
| пуш не прошёл в один из remotes | `⚠️ Дашборд обновлён с замечанием` | данные пересчитаны и закоммичены, на Amvera уедут после ручного пуша; прогон продолжается |
| падение пайплайна | `❌ Автопрогон дашборда упал` | выход, справка не собирается |

Лог — `logs/auto-pipeline.log` (в git не идёт, подрезается на 2000 строк), плюс
всплывашка macOS через `osascript`.

### Управление

```bash
./automation/install.sh              # установить и включить
./automation/install.sh --status     # загружен ли агент
./automation/install.sh --uninstall  # выключить и убрать

./watch_pipeline.sh --dry-run        # что было бы сделано, без записи
./watch_pipeline.sh --force          # прогнать, даже если выгрузка уже обработана
```
