# Transformation Dashboard

## Система работы (vz-system)
Проект — часть общей системы. База (скиллы/агенты/ревью) приезжает **установленным
плагином** `vz-system` (источник — `~/Projects/claude-system`, scope `user` → доступен
во всех проектах; ставить в проект ничего не нужно). Скиллы вызываются **с namespace**:
`/vz-system:vzgoal`, `/vz-system:night`, `/vz-system:morning`, `/vz-system:close`,
`/vz-system:graphify`, `/vz-system:retro`; агенты — тоже с namespace: `vz-system:reviewer`, `vz-system:plan-reviewer` (голое имя = жёсткая ошибка резолвинга).
- **Актуальный состав базы — `claude plugin details vz-system`.** Список выше может
  отстать; при расхождении верна команда, а не список.
- Концепт: `~/Projects/claude-system/CONCEPT.md`
- Карта возможностей (куда идти за чем): `~/Projects/claude-system/CAPABILITIES.md`
- Протокол ночной шины: `~/Projects/shared/CLAUDE.md`

**Локальные скиллы/агенты:** `pipeline-preview` (`.claude/skills/pipeline-preview/`) —
прогон пайплайна на копиях и diff «до/после» без записи в корень проекта;
`upcoming-report` (`.claude/skills/upcoming-report/`) — справка по задачам с приближающимся
сроком за произвольное окно дат (txt + md).
**Локальные нюансы:** дашборд мониторинга проектов (Excel → `data.json` → `index.html`, ES-модули), деплой на Amvera через Docker; детали — в разделах ниже.

Дашборд мониторинга проектов трансформации. Данные извлекаются из Excel-файлов в `data.json`, который отображается в `index.html`.

## Роли в работе над проектом

- **Claude.ai (этот проект)** — планирование, концепция, постановка задач, обсуждение логики
- **Claude Code** — написание и изменение кода, обновление `CLAUDE.md` после каждой сессии

### Регламент обновления CLAUDE.md

После каждой рабочей сессии Claude Code **обязан**:
1. Дописать в `## История изменений` все изменения этой сессии (дата + краткое описание)
2. Обновить затронутые разделы документации (структура данных, формат сообщений, логика)
3. Закоммитить `CLAUDE.md` вместе с изменёнными файлами одним коммитом

Формат записи в истории: `| ГГГГ-ММ-ДД | Файл: описание изменения |`

## Правило: пробные прогоны — только в песочнице

`extract_data.py`, `process_report.py` и `overdue_report.py` пишут результат **в текущий
каталог**: `data.json` (+ `.bak`), `telegram_priority_*.txt` / `telegram_transform_*.txt`,
`overdue_tasks_*.txt`. Поэтому любой проверочный запуск делается **на копиях**:

```bash
SP=/tmp/preview && mkdir -p $SP
cp extract_data.py process_report.py config.py data.json "ОТЧЕТ_ДД.ММ.md" $SP/
cd $SP && python3 process_report.py "ОТЧЕТ_ДД.ММ.md" --telegram-only
```

В корне проекта пайплайн запускает **владелец** — когда еженедельный отчёт полностью
собран (`./deploy.sh …`). Ассистент туда не пишет: прогон на недособранном отчёте
затрёт рабочие файлы и отправит в `⚠️ ИНФОРМАЦИЯ НЕ ПРЕДСТАВЛЕНА` проекты, статус
по которым просто ещё не внесён.

Ручное копирование заменяет локальный скилл `pipeline-preview` — он гоняет текущую
и базовую версии скриптов на одних входах и показывает diff `data.json` и
telegram-сообщений плюс проверку сходимости шт.ед.:

```bash
.claude/skills/pipeline-preview/preview.sh                 # свежий отчёт + предыдущий
.claude/skills/pipeline-preview/preview.sh --stage extract # только extract_data.py
.claude/skills/pipeline-preview/preview.sh --base HEAD~3   # сравнить с другой ревизией
```

## Обновление данных

> **Ежедневное обновление происходит само** — достаточно положить выгрузку Redmine
> в корень проекта, остальное делает LaunchAgent (см. «Автопрогон по свежей выгрузке»).
> Разделы ниже — про ручной запуск: он нужен для **еженедельной telegram-сводки**
> (`$2` — md-отчёт), которую автопрогон намеренно не трогает.

**Быстрый вариант** (одна команда):
```bash
./deploy.sh issues_16.06.xlsx ОТЧЕТ_10.06.md ОТЧЕТ_03.06.md
# $1 — xlsx Redmine, $2 — md-отчёт, $3 — предыдущий md для diff (необязателен),
# $4 — штатка, $5 — файл высвобождения (оба необязательны)
```
Штатка и файл высвобождения (`$4`/`$5`) по умолчанию определяются автоматически: берётся самый
свежий подходящий файл в корне по времени изменения (`ls -t` по `ШТАТКА_ДБ*.xlsx` и
`*Данные по высвобождению*.xlsx`, `shopt -s nullglob`), иначе — каноническое имя. Выбранные файлы
печатаются в лог.

Пайплайн скрипта: `extract_data.py $1 $4 $5` → `process_report.py $2 [--prev $3]` →
`overdue_report.py` → `git add data.json && git commit -- data.json` → `git push` в каждый
настроенный remote (`upstream`, `origin`); падение одного не блокирует остальные.
Скрипт останавливается, если HEAD не на `main` (пуш идёт в `main`, и «запушено» было бы
неправдой), а `pathspec` в коммите обязателен: без него в публичный репозиторий уезжает
всё, что лежит в индексе, — а рядом с автопрогоном человека, который это заметит, нет.

⚠️ **Пуш уносит ветку целиком, а не только `data.json`.** Любой локально закоммиченный
код уедет в оба GitHub-remote при следующем же прогоне — в том числе автоматическом,
по заброшенному в папку файлу. Правки, которые не должны уходить наружу, держать
незакоммиченными или в отдельной ветке.

**Вручную:**
1. Положить актуальные `.xlsx` файлы в папку проекта (в git не попадут — в `.gitignore`)
2. Запустить скрипт:
   ```bash
   python3 extract_data.py
   # или с явным именем файла Redmine:
   python3 extract_data.py "issues (1).xlsx"
   # или все три файла явно (redmine, штатка, высвобождение):
   python3 extract_data.py issues_15.06.xlsx ШТАТКА_ДБ_15.06.2026.xlsx "Проекты_Данные по высвобождению_15.06.2026.xlsx"
   ```
   Аргументы `$2` (штатка) и `$3` (файл высвобождения) опциональны; по умолчанию — канонические имена `ШТАТКА_ДБ.xlsx` / `ПРОЕКТЫ_Данные по высвобождению.xlsx`.
3. Закоммитить обновлённый `data.json`:
   ```bash
   git add data.json
   git commit -m "update data.json"
   git push
   ```

## Автопрогон по свежей выгрузке (`watch_pipeline.sh`)

Выгрузку из Redmine достаточно **положить в корень проекта** — остальное происходит само.
Триггер — LaunchAgent `com.vz.transformation-pipeline` с `WatchPaths` на папку проекта;
он будит `watch_pipeline.sh` на любое изменение папки, а решение «работать или выйти»
скрипт принимает сам.

Что делает прогон:
1. переименовывает выгрузку в `issues_ДД.ММ.xlsx` по **сегодняшней дате**;
2. `./deploy.sh <файл>` — `extract_data.py` → `overdue_report.py` → коммит `data.json` → пуш;
3. `upcoming_report.py --to <пятница>` — справка по срокам от сегодня до конца недели.

**Повторный заброс в тот же день** проходит цикл заново: файл дня перезаписывается молча,
данные пересчитываются. Так вечерняя картина замещает утреннюю (задачи, закрытые за день).

**Еженедельная telegram-сводка здесь не собирается.** `deploy.sh` вызывается без `$2`,
поэтому `process_report.py` не запускается: он читает `ОТЧЕТ_ДД.ММ.md`, и автопрогон
в середине недели собрал бы сводку по прошлонедельному отчёту. Сводку по-прежнему делает
владелец — `./deploy.sh issues_ДД.ММ.xlsx ОТЧЕТ_ДД.ММ.md ОТЧЕТ_предыдущий.md`.

### Почему прогон не зацикливается

Пайплайн сам пишет в ту же папку (`data.json`, `overdue_tasks_*.txt`, справки) — каждая
запись снова будит launchd. Три предохранителя:

| Предохранитель | Что закрывает |
|----------------|---------------|
| Замок `logs/.lock` (каталог + PID внутри) | наложение прогонов. Снимается только замок **мёртвого** процесса (`kill -0`): застрявший на 40 минут `git push` жив, и отбирать у него замок нельзя. `trap` удаляет замок, только если он всё ещё свой |
| Отпечаток `logs/.processed` — `<статус> <mtime\|размер> <pid>`, пишется **до** работы | собственные записи скрипта — и повтор упавшего прогона. `started` → работа идёт, `done`/`failed` → попытка завершена, повтор только по `--force`. Иначе падение `deploy.sh` уводило бы скрипт в бесконечный цикл коммитов, пушей и сообщений об ошибке |
| Статус `started` + **мёртвый** pid = оборванный прогон | launchd шлёт SIGTERM при выходе из системы, и убитый на середине прогон без статуса выглядел бы обработанным: выгрузка молча пропала бы, а `data.json` остался вчерашним. Такой прогон повторяется, и в итоговом сообщении появляется строка «↻ прошлый прогон был оборван» |
| «Только сегодняшняя выгрузка» (mtime ≥ начала дня) | посторонний будильник от правки кода не переименует вчерашний файл в сегодняшний |
| Дата в имени = сегодня | старый снимок, вернувшийся в корень (`cp archive/issues/…` даёт свежий mtime), не уедет на дашборд как актуальные данные |
| Проверка колонок Redmine **до** `mv` | `mv -f` затирает снимок дня безвозвратно (выгрузки в git не хранятся), а маска `issues*.xlsx` ловит любой файл на «issues». Требования те же, что у пайплайна — `extract_data.validate_source_columns` |
| Замок берётся максимум за три попытки | `mkdir` может не выполняться и не из-за чужого замка (каталог недоступен, нет места). Бесконечный цикл занял бы метку агента навсегда: launchd не поднимет второй экземпляр, и автопрогон встанет молча |

**Проверка различает два исхода.** Код возврата `2` — файл действительно чужой
(нет обязательных колонок): выгрузка помечается обработанной, уходит сообщение.
Код `3` — проверку **не удалось выполнить** (рассинхрон numpy/pandas, недоступный
файл): отпечаток НЕ пишется, потому что диагноз неизвестен, и после починки среды
выгрузка подхватится сама. Сообщение в этом случае гасится через `logs/.skipped`.

**Отбракованный файл не пропадает молча.** Если выгрузка не прошла проверку по дате
или по колонкам, об этом уходит сообщение с подсказкой `--force`, а её отпечаток
запоминается в `logs/.skipped`, чтобы не повторять это на каждое пробуждение
(их порядка шести в минуту). Причина: файл, скачанный вечером и перенесённый в папку
утром, сохраняет старый mtime — а тишину владелец читает как «всё прошло».


Кандидат — самый свежий по mtime файл `issues*.xlsx` в корне (`issues.xlsx`,
`issues (1).xlsx` — как скачалось). Перед работой скрипт ждёт, пока размер файла
перестанет меняться (докачка браузером), максимум ~10 с.

### Часовой пояс

Даты берутся по `TZ=Europe/Moscow`: машина стоит в `America/New_York`, а выгрузка
приходит утром по Москве — по локальному времени она получила бы вчерашнее число.
Тот же пояс у соседнего агента `LIFE/bin/redmine_watch.py`, иначе имена снимков
`issues_ДД.ММ.xlsx` разъехались бы между ними. Оба агента висят на одной папке и не
мешают друг другу: наш нормализует имя, которого тот ждёт.

### Итог прогона: Telegram + всплывашка + лог

Каждый прогон заканчивается **сообщением в Telegram** — владелец не должен заглядывать
в папку, чтобы понять, закончилась работа или нет. Канал тот же, что у
`LIFE/bin/redmine_watch.py`: `python3 ~/Projects/LIFE/bin/tg.py "текст"` (токен в keychain
`vz-telegram-bot`, chat_id в `shared/telegram/state.json`). Недоставленное сообщение
прогон не роняет — пишется предупреждение в лог.

Успешный прогон — файл, цифры из свежего `data.json` (проекты/задачи/просрочки/%
высвобождения), сводка справки с именем файла и статус пуша. Цифры важны: «готово»
без них не отвечает на вопрос, та ли выгрузка обработана.

**Сбой** уходит отдельным сообщением: шаг, код возврата, хвост лога **текущего прогона**
(`log_tail` режет по маркеру `─── новая выгрузка`, иначе затекает история прошлых),
команда повтора `./watch_pipeline.sh --force` и путь к полному логу. Функция `fail`
зовётся перед каждым аварийным выходом — тишина в Telegram никогда не означает
«прогон прошёл».

Исходы `deploy.sh` разведены по трём сообщениям:

| Исход | Заголовок | Что дальше |
|-------|-----------|-----------|
| успех / «данные не изменились» | `✅ Дашборд обновлён` | справка собирается, прогон завершён |
| пуш не прошёл в один из remotes | `⚠️ Дашборд обновлён с замечанием` | данные пересчитаны и закоммичены, на Amvera уедут после ручного пуша; прогон продолжается |
| падение пайплайна | `❌ Автопрогон дашборда упал` | выход, справка не собирается |

Лог — `logs/auto-pipeline.log` (в git не идёт, подрезается на 2000 строк), плюс
всплывашка macOS через `osascript`.

## Сбор еженедельных отчётов через Telegram (`report_inbox.py`)

Отчёты по проектам приходят владельцу в мессенджер блоками. Раньше он собирал
`ОТЧЕТ_ДД.ММ.md` вручную; теперь блоки пересылаются боту `@ZVVChannel_bot`
(`~/Projects/shared/bin/telegram-bot.py`), а тот складывает их через `report_inbox.py`.

**Парсер не писался.** Формат присылаемых блоков совпадает с тем, что уже читает
`process_report.parse_report`: шапка «ЕЖЕНЕДЕЛЬНЫЙ ОТЧЁТ» игнорируется, строка-
разделитель `▬▬▬ 🔵 ПРОЕКТЫ ТРАНСФОРМАЦИИ ▬▬▬` распознаётся как заголовок группы,
блоки разбираются с `👤`, `🔗`, `✅`, `📍`.

### Как это работает

| Шаг | Что происходит |
|-----|----------------|
| Приём | Проект опознаётся **по ссылке** на Redmine (точно); резерв — нечёткое имя через `find_in_data`. При совпадении по имени бот пишет «(по названию «…»)» — чтобы владелец перепроверил |
| Хранение | `report_inbox/current/<issue_id>.md` + `_meta.json`; повторная присылка **заменяет** блок, а не множит. В git не идёт |
| Список ожидания | Активные проекты из `data.json` — обновляется вслед за Redmine сам (на 26.08.2026 их 17) |
| Сборка | Когда сдали все — `build` идёт сам: собирает `ОТЧЕТ_ДД.ММ.md`, зовёт `process_report.py` с `--prev` (свежайший прошлый отчёт) и отдаёт обе сводки |
| Закрытие недели | После **полной** сборки цикл архивируется в `report_inbox/ГГГГ-ММ-ДД/`. Иначе следующая неделя началась бы с «все сдали», а новые отчёты шли бы как правки. При `--force` (собрали без опоздавших) неделя остаётся открытой |

Название проекта в собранный отчёт идёт **каноническое из `data.json`**, а не как
прислали: присылают вразнобой (капсом, своей формулировкой), а сводка уходит
руководству.

### Со стороны бота

Команду помнить не нужно — бот узнаёт отчёт сам:

- **строгий признак** — строка с 🔵/🔴 плюс ссылка на Redmine или секция отчёта;
- **достройка** — блок скопирован без строки «🔵 Название» (так копируют из уже
  отправленной сводки): если в тексте ровно одна ссылка на задачу **и** есть секция
  `✅ Выполнено` / `📍 Текущие этапы`, строка достраивается. Проект определяется по
  ссылке, имя всё равно берётся из `data.json`. Без секции текст не трогается —
  иначе обычная задача «посмотри issues/123, там ошибка» уехала бы в отчёты;
- иначе сообщение уходит в handoff-шину и становится брифом на разработку —
  ровно это случилось 26.08 с блоком без 🔵.

Под ответами — кнопки «Кого ждём», «Собрать», «Закрыть неделю», «Выйти»; слова
«отчёты», «сводка» работают как `/report`; незакрытый сбор виден в общем `/status`.
Лейн закрывается сам через 12 часов.

### Живость бота

Бот работает на ноутбуке владельца: пока крышка закрыта, он спит. **Сообщения при
этом не теряются** — Telegram хранит их сутки и отдаёт при следующем опросе.

- каждый круг опроса пишется отметка `shared/telegram/heartbeat`;
- при старте бот сравнивает её с текущим временем и, если пропадал дольше пяти
  минут, сам докладывает: «🔌 Снова на связи, меня не было 3 ч 15 мин»;
- `/ping` (или «жив?») отвечает, когда был последний опрос.

## Кураторы и высвобождение

Кураторы направлений (с 15.06.2026 — четыре): `Кренёва А.А. → Родевальд С.Е. → Гуляев В.А. → Кудряшов Е.С.`
`Комитет и РЦТ` = сумма всех групп кураторов
Формула %: `высвобождение шт.ед. / план_20% × 100`

### Формат файла высвобождения и матчинг (с 15.06.2026)
Новый файл высвобождения содержит колонку **`Ответственный`**: итоги по куратору лежат
в строках-заголовках (где `Ответственный` заполнен, а `Проект` пуст), ниже — строки проектов.
Скрипт автоопределяет формат по наличию колонки `Ответственный` (иначе — старый формат с NaN-строками).

Имена кураторов отличаются между источниками, поэтому матчинг идёт **по фамилии** (`curator_key`):
нормализация — первое слово, lowercase, `ё→е`. Написание различается:
- Redmine (owner): `Кренева`, `Кудряшов` (через «о»)
- Штатка / высвобождение: `Кренёва` (через «ё»), `Кудряшев` (через «е» — опечатка)

**Правильное написание — `Кудряшов`** (как в Redmine). В `extract_data.py` опечатки имён
исправляются через `CURATOR_NAME_FIX` / `canon_name` (`Кудряшев → Кудряшов`) до записи в `data.json`,
чтобы карточка куратора и owner-фильтр дашборда совпадали.

### Доли кураторов: один проект — несколько строк

Проект, который ведут несколько кураторов, разнесён в файле высвобождения по строкам-долям
(строка лежит в блоке своего куратора — по строке-заголовку `Ответственный` выше).
Величина по проекту = **сумма долей**: `extract_data.py` аккумулирует строки одного проекта
(`VYSV_SUM_FIELDS` через `sum_opt`), а не берёт последнюю. Ссылка (`url`) — первая непустая.

Пример (15.06.2026): «Цифровой двойник сотрудника (ИИ)» — 3 строки (Кренёва 5760/2329,
Гуляев 1409/0, Кудряшов 919/0) → внутр. 8088 ч, внеш. 2329 ч; «Анализ проектов ГЧП» —
2 строки (Родевальд + Кудряшов) → 1824 ч.

**Контроль сходимости:** сумма `total_units` по всем проектам должна совпадать с
`vysv_units` куратора «Комитет и РЦТ» (32.30 на 15.06.2026). До суммирования долей
расхождение составляло 27.89 против 32.30.

### Матчинг проектов с файлом высвобождения

Названия проектов расходятся между источниками (в Redmine — `Цифровое нормирование 2.0`,
в файле высвобождения — `Цифровое нормирование`), поэтому сопоставление идёт по
нормализованному ключу `project_key()`: lowercase, `ё→е`, отброшен хвост-версия (`2.0`),
только буквы/цифры через один пробел. Хвост вида `223-ФЗ` версией не считается —
такие проекты не схлопываются.

`extract_data.py` печатает в лог диагностики:
- `Σ проекты, разнесённые по долям кураторов` — сколько строк просуммировано;
- `~ сопоставлены по нормализованному имени` — названия в источниках разошлись (стоит выровнять);
- `⚠️ активные проекты без строки в файле высвобождения` — часы останутся пустыми,
  и на дашборде/в Telegram блок «📉 Высвобождение» у такого проекта не появится;
- `⚠️ неоднозначные названия проектов` — если в Redmine появятся сразу «X» и «X 2.0»,
  их ключи совпадут и неясно, какому из них принадлежит строка высвобождения.
  Данные в этом случае **не применяются к обоим** (иначе цифры задвоятся) — нужно
  развести названия в источниках.

> ⚠️ `fact_hours` тоже суммируется по строкам-долям. Сегодня факт заполнен только у
> однострочных проектов, но если в новой выгрузке автор проставит факт как итог по
> проекту в каждой доле, значение удвоится — проверять при смене формата файла.

Соответствие колонок (новый/старый формат, см. `cell_any`):
- шт.ед.: `План, шт. ед.` / `высвобождение, шт. ед.`
- внешнее: `Внешнее высвобождение` / `Внешнее высвобождение, часы`
- внутреннее: `Внутрнее высвобождение` / `Внутреннее высвобождение`

## Еженедельный отчёт (`process_report.py`)

Скрипт обрабатывает еженедельный `.md`-файл с отчётами по проектам.

### Запуск

```bash
python3 process_report.py ОТЧЕТ_01_04.md
python3 process_report.py ОТЧЕТ_01_04.md --telegram-only   # только файлы Telegram
python3 process_report.py ОТЧЕТ_01_04.md --no-telegram     # только обновить data.json
python3 process_report.py ОТЧЕТ_01_04.md --data data.json  # явный путь к data.json
python3 process_report.py ОТЧЕТ_08_04.md --prev ОТЧЕТ_02_04.md  # diff с предыдущим
```

### Что делает

1. Парсит `.md`-файл (блоки `✅ Выполнено` и `📍 Текущие этапы`)
2. Сопоставляет проекты с `data.json` — по ID из URL `🔗`, резерв: нечёткое совпадение имён (`difflib`, порог 0.6)
3. Пишет `current_status` в найденные проекты
4. Делает резервную копию `data.json.bak`
5. Генерирует **два файла** Telegram-сообщений

### Выходные файлы

| Файл | Содержимое |
|------|-----------|
| `telegram_priority_ДД_ММ_ГГГГ.txt` | Приоритетные проекты (`is_priority=true`) |
| `telegram_transform_ДД_ММ_ГГГГ.txt` | Трансформационные проекты (`is_priority=false`) |

### Формат Telegram-сообщения

- Строка портфеля в шапке: `📈 Портфель: 20 · ✅ реализовано 2 · 🔄 в работе 18` (только текущий год)
- Секция `✅ РЕАЛИЗОВАНО В 2026 (N)` — сразу после шапки, до проектов в работе
- Заголовок группы со счётчиком: `🔴 ПРИОРИТЕТНЫЕ ПРОЕКТЫ (3)`
- Нумерация проектов внутри группы: `1. 🔴 Электронные ДС с ПИК`
- Сортировка по возрастанию дедлайна
- Секция `⚠️ ИНФОРМАЦИЯ НЕ ПРЕДСТАВЛЕНА` (если есть активные проекты без отчёта)
- Без Markdown-символов (`*`, `_`) — текст готов к ручному копированию в Telegram

Формат одного проекта:
```
1. 🔵 Название проекта
👤 Кренёва А.А.
🔗 https://transformation.rm.mosreg.ru/#/issues/12345
📉 Высвобождение:
   Внутреннее: 9920 ч / 5.03 шт.ед.
   Внешнее:    43340 ч / 21.98 шт.ед.

✅ Выполнено:
...

📍 В работе:
...

ℹ️ Дополнительно:
...
─────────────────
```

Логика полей:
- `👤` — `owner_short` из `data.json` (Ответственный из Redmine, совпадает с фильтром дашборда); резерв — `person` из строки `👤` в MD-файле
- `🔗` — URL из строки `🔗` в MD-файле или поле `url` из `data.json`
- `📉 Высвобождение` — строка выводится только если часы > 0; шт.ед. = часы / 1972; блок скрывается целиком если все значения None или 0
- `ℹ️ Дополнительно` — примечание к проекту из MD-отчёта (см. «Примечания к проекту»); при `--prev` получает `🆕`, если текст изменился

### Секция «Реализовано» (закрытые проекты)

Закрытые проекты не попадают в MD-отчёт, поэтому берутся напрямую из `data.json`
(`status ∈ CLOSED_STATUSES`) — иначе результат года не виден в сводке.

- **Только текущий год** (`config.YEAR`): проекты, закрытые в прошлые годы, в сообщение не попадают
- Дата реализации — поле `closed_at` («Закрыта»), резерв — `defense_at` («Дата и время защиты»);
  проект без обеих дат в секцию не попадает
- Сортировка — от свежих к старым; строка проекта: `N. Название — ДД.ММ.ГГГГ · Ответственный` + `🔗` ссылка
- Ссылка: поле `url`, резерв — `{REDMINE_BASE}/{id}`
- Счётчики шапки: «реализовано» = размер секции (за год), «в работе» = активные проекты
  группы из `data.json` (а не число проектов в MD-отчёте — чтобы не «поехало», если кто-то не сдал статус)
- **Проект, закрытый на отчётной неделе**, ещё присутствует в MD-отчёте: его блок исключается
  из списка «в работе» и остаётся только в секции «Реализовано» — иначе он был бы одновременно
  реализованным и в работе, а счётчик группы разошёлся бы с «в работе N». Исключаются **только те**,
  что реально попали в секцию (`in_completed_section` сверяет объекты со списком `collect_completed`):
  закрытый проект прошлого года или без даты закрытия остаётся в списке отчёта, иначе он исчез бы
  из сообщения совсем. Скрипт печатает перенесённые проекты в лог; `current_status` из отчёта
  при этом сохраняется в `data.json` (фильтр действует только на Telegram-сообщения)
- Строка портфеля выводится, только когда есть `data.json` (при `--telegram-only` без него счётчики
  не с чем сверить); при нуле реализованных выводится `✅ реализовано 0`, а секция не рендерится
- Закрытые проекты без `closed_at` и `defense_at` в секцию не попадают — скрипт предупреждает о них в логе

| Функция | Назначение |
|---------|-----------|
| `completed_date(dp)` | Дата реализации: `closed_at` → `defense_at` → None |
| `collect_completed(projects, priority, year=YEAR)` | Закрытые проекты группы за год, свежие первыми |
| `project_url(dp)` | Ссылка на проект: `url` → `{REDMINE_BASE}/{id}` |
| `_portfolio_line(completed, in_work_count)` | Строка `📈 Портфель: …` для шапки |
| `_render_completed(out, projects, year)` | Секция `✅ РЕАЛИЗОВАНО В ГГГГ (N)` |
| `in_completed_section(proj, completed)` | Проект из MD-отчёта, попавший в секцию «Реализовано» (исключается из группы «в работе») |

### Примечания к проекту (`ℹ️ Дополнительно`)

Свободный абзац в конце блока `✅`/`📍` в MD-отчёте — это примечание к проекту
(«необходим перенос сроков…», «проведено ВКС совещание…»), а не очередной этап.
`split_note()` отделяет его от тела блока; в Telegram-сообщении он выводится
отдельным блоком `ℹ️ Дополнительно:` и пишется в `current_status` (виден на дашборде).

Абзац считается примечанием, если он последний в блоке **и**:
- помечен явно: `ℹ️` / `📝` / `💬` / `❗` / `Примечание:` / `Прим.` / `Доп. информация:` /
  `Дополнительно:` / `Справочно:` — **рекомендуемый способ, срабатывает всегда**; или
- это связный текст: нет строк-пунктов (`•`, `-`, `1.`, `Этап…`) и есть строка
  длиной ≥ `NOTE_MIN_FREE_TEXT_LEN` (100 символов) — так короткие подпункты этапов
  не принимаются за примечание

Даты в начале строки (`11.06.2026 с Мингос проведено…`) нумерацией не считаются
(`LIST_ITEM_RE` требует `\d{1,2}[.)]` без цифры следом).

### Признак приоритетности

Поле `is_priority` в `data.json` — извлекается из колонки **«Приоритетный проект»** файла Redmine.
`is_priority = true` если значение `'Да'`.
При ручном редактировании `data.json` поле можно проставить напрямую.

### Diff-режим (`--prev`)

Флаг `--prev PREV_REPORT` включает сравнение текущего отчёта с предыдущим.

**Что меняется в выводе:**
- Шапка сообщений: `🔄 Сравнение с отчётом от ДД.ММ.ГГГГ`
- Строки «В работе», которых не было в предыдущем «В работе» → префикс `🆕`
- Строки «Выполнено», которых не было ни в «Выполнено» ни в «В работе» предыдущего → `🆕`
- Проект, отсутствующий в предыдущем отчёте → суффикс `🆕 новый проект` в заголовке

**Вспомогательные функции diff:**

| Функция | Назначение |
|---------|-----------|
| `strip_dates(s)` | Удаляет `(дд.мм)` / `(дд.мм.гггг)` перед сравнением |
| `normalize_line(s)` | Убирает `•`, `-`, `1.`, лишние пробелы; lowercase |
| `_text_to_norm_set(text)` | Текст → множество нормализованных строк |
| `compute_new_lines(cur, prev_comp, prev_cur)` | Строки текущего блока, отсутствующие в предыдущем |
| `find_prev_project(proj, prev_index)` | Матчинг по `issue_id`, резерв — нечёткое имя |
| `build_prev_index(prev_groups)` | Строит `{by_id, by_name}` из разобранного предыдущего отчёта |
| `render_block_with_diff(block_text, new_lines_set)` | Вставляет `🆕 ` перед новыми строками |

Без `--prev` поведение идентично прежнему.

### Парсер `📍`-строк

Поддерживаемые форматы заголовка блока «В работе» в MD-файле:

- `📍 Текущие этапы:`

## Отчёт по просроченным задачам (`overdue_report.py`)

Скрипт формирует текстовый отчёт по всем просроченным задачам **и задачам со сроком сегодня** из `data.json`.

### Запуск

```bash
python3 overdue_report.py
python3 overdue_report.py --data data.json
python3 overdue_report.py --output overdue_tasks_28_05_2026.txt
```

Вызывается автоматически из `deploy.sh` после `extract_data.py` и `process_report.py`.

### Что делает

1. Читает `data.json` (берёт `all_tasks` и `projects`).
2. Отбирает задачи: дедлайн ≤ сегодня **и** статус ∉ `CLOSED_STATUSES` (`Закрыта`, `Закрыто`, `Выполнено`, `Выполнена`, `Завершена`).
3. Группирует по полю `project` (имя проекта, как в задаче) → матч с `projects[]` по имени.
4. Сортировка проектов: max дней просрочки убыв., затем по суммарному кол-ву задач убыв., затем по имени.
5. Сортировка задач внутри проекта: дней просрочки убыв.; задачи разделяются на две подсекции — `⏰ Просроченные задачи (N)` и `📅 Срок сегодня (N)`.
6. Сохраняет `overdue_tasks_DD_MM_YYYY.txt`.

### Формат сообщения

```
📊 Отчёт по просроченным и сегодняшним задачам
Дата: 29.05.2026
Всего: просрочено 1 задача, со сроком сегодня 5 задач в 2 проектах

━━━━━━━━━━━━━━━━

1. 🔵 Имя проекта
👤 Ответственный: Иванов И.И.
🔗 https://transformation.rm.mosreg.ru/#/issues/12345

⏰ Просроченные задачи (1):
   • Тема задачи
     👤 Петров П.П.
     📅 Дедлайн: 15.05.2026 (просрочено на 13 дн.)
     📌 Статус: Новая
     🔗 https://transformation.rm.mosreg.ru/#/issues/13488

📅 Срок сегодня (1):
   • Другая тема
     👤 Сидоров С.С.
     📅 Дедлайн: 29.05.2026 (сегодня)
     📌 Статус: В работе
     🔗 https://transformation.rm.mosreg.ru/#/issues/13500
─────────────────
```

- `🔴` для приоритетных проектов (`is_priority=true`), `🔵` — для остальных.
- Подсекции внутри проекта рендерятся только если соответствующие задачи есть.
- Если задач нет — выводится «✅ Просроченных и сегодняшних задач нет.».

### Ключевые функции

| Функция | Назначение |
|---------|-----------|
| `parse_deadline(s)` | `DD.MM.YYYY` → `date` или `None` |
| `collect_overdue(data, today)` | Группировка задач (дедлайн ≤ today) по проектам с агрегатами `max_overdue` / `total_overdue` / `total_today` / `total` |
| `plural_days(n)` / `plural_tasks(n)` / `plural_projects(n)` | Русская грамматика числительных |
| `_render_task(t, today_task)` | Строки одной задачи; флаг `today_task` управляет надписью даты |
| `build_message(groups, today)` | Сборка текста отчёта (две подсекции: просроченные + срок сегодня) |

## Справка по приближающимся срокам (`upcoming_report.py`)

`overdue_report.py` смотрит назад («что уже просрочено / горит сегодня»),
`upcoming_report.py` — вперёд: **какие задачи уйдут в просрочку**, если не закрыть их
в срок. Окно дат задаётся аргументами; результат выгружается в двух форматах.

### Запуск

```bash
python3 upcoming_report.py                        # сегодня .. +7 дней, txt + md
python3 upcoming_report.py --to 17.08.2026        # сегодня .. конкретная дата
python3 upcoming_report.py --days 4               # сегодня .. +4 дня
python3 upcoming_report.py --from 18.08.2026 --to 24.08.2026
python3 upcoming_report.py --format md            # txt | md | both (по умолчанию both)
python3 upcoming_report.py --include-overdue      # добавить ранее просроченные
python3 upcoming_report.py --stdout               # в консоль, без записи файлов
python3 upcoming_report.py --outdir /tmp/x --output ИМЯ --data data.json
```

Обёртка — локальный скилл `.claude/skills/upcoming-report/` (когда просят «справку
по срокам», «что горит на этой неделе», «задачи до ДД.ММ»).

### Выходные файлы

| Файл | Содержимое |
|------|-----------|
| `СПРАВКА_сроки_13-17.08.2026.txt` | Формат `overdue_tasks_*.txt` — готов к копированию в Telegram |
| `СПРАВКА_сроки_13-17.08.2026.md`  | Формат `СПРАВКА_*.md`: шапка + разбивка по датам, Часть 1 (детализация таблицами по проектам), Часть 2 (краткая сводка), Часть 3 («Обратить внимание») |

Имя формируется из окна (`window_slug`): один месяц → `13-17.08.2026`, разные месяцы →
`29.08-04.09.2026`, разные годы → `30.12.2026-05.01.2027`. Переопределяется `--output`.

> Справки **в git не хранятся** — это рабочие выгрузки под конкретную дату:
> `.txt` покрыт общим правилом `*.txt`, для markdown в `.gitignore` есть `СПРАВКА_*.md`.
> Пересобираются командой из актуального `data.json` в любой момент.

### Логика

- Отбор: дедлайн в `[--from .. --to]` включительно **и** статус ∉ `CLOSED_STATUSES`.
- Группировка по проекту (ответственный, ссылка, `is_priority` — из `projects[]`);
  группы сортируются по ближайшему сроку, задачи внутри — по дате.
- Задачи левее окна в справку не входят (только справочная строка) — для них
  `overdue_report.py`; `--include-overdue` сводит всё в один документ.
- **Два счётчика за левой границей** (`collect_window` → `stats`): `before_window`
  (срок < начала окна) и `overdue_now` (из них просрочено на сегодня). Различаются,
  когда окно начинается в будущем, — формулировку выбирает `before_window_line`.
- Имя выгрузки Redmine в шапке md определяется `detect_source`: файл `issues*.xlsx`
  рядом с `data.json`, mtime которого совпадает с `updated_at` (±60 c).
- Скрипт только **читает** `data.json`; пайплайн не запускает, рабочие файлы не трогает.
  Свежесть справки = свежесть `data.json` (обновляет владелец через `./deploy.sh`).

### Ключевые функции

| Функция | Назначение |
|---------|-----------|
| `parse_date_arg(s)` / `resolve_window(start, end, days, today)` | Разбор дат CLI и границы окна (умолчание — `DEFAULT_DAYS=7`); перевёрнутое окно → `ValueError` → `ap.error` |
| `window_slug(start, end)` / `window_title(start, end, with_year)` | Имя файла и заголовок периода |
| `collect_window(data, start, end, today, include_overdue)` | Группы задач + `stats` (`before_window` / `overdue_now`) |
| `before_window_line(stats, start, today, bold)` | Справочная строка про задачи левее окна (`bold` — для markdown) |
| `tasks_by_day(groups)` / `tasks_by_status(groups)` | Агрегаты для разбивки по датам и блока «Обратить внимание» |
| `time_left(days, style)` | «сегодня» / «завтра (1 день)» / «4 дня» (md) против «завтра, через 1 день» / «через 4 дня» (txt) |
| `detect_source(data_path, updated_at)` | Имя выгрузки `issues*.xlsx`, из которой собран `data.json` |
| `build_txt(...)` / `build_md(...)` | Рендер двух форматов |
