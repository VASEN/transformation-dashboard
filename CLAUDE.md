# Transformation Dashboard

## Система работы (vz-system)
Проект — часть общей системы. База (скиллы/агенты/ревью) приезжает **установленным
плагином** `vz-system` (источник — `~/Projects/claude-system`, scope `user` → доступен
во всех проектах; ставить в проект ничего не нужно). Скиллы вызываются **с namespace**:
`/vz-system:vzgoal`, `/vz-system:night`, `/vz-system:morning`, `/vz-system:close`,
`/vz-system:graphify`, `/vz-system:retro`; агенты — тоже с namespace: `vz-system:reviewer`, `vz-system:plan-reviewer` (голое имя = жёсткая ошибка резолвинга).
- **Актуальный состав базы — `claude plugin details vz-system`.** Список выше может
  отстать; при расхождении верна команда, а не список.
- Концепт: `~/Projects/claude-system/CONCEPT.md`
- Карта возможностей (куда идти за чем): `~/Projects/claude-system/CAPABILITIES.md`
- Протокол ночной шины: `~/Projects/shared/CLAUDE.md`

**Локальные скиллы/агенты:** `pipeline-preview` (`.claude/skills/pipeline-preview/`) —
прогон пайплайна на копиях и diff «до/после» без записи в корень проекта;
`upcoming-report` (`.claude/skills/upcoming-report/`) — справка по задачам с приближающимся
сроком за произвольное окно дат (txt + md).
**Локальные нюансы:** дашборд мониторинга проектов (Excel → `data.json` → `index.html`, ES-модули), деплой на Amvera через Docker; детали — в разделах ниже.

Дашборд мониторинга проектов трансформации. Данные извлекаются из Excel-файлов в `data.json`, который отображается в `index.html`.

## Роли в работе над проектом

- **Claude.ai (этот проект)** — планирование, концепция, постановка задач, обсуждение логики
- **Claude Code** — написание и изменение кода, обновление `CLAUDE.md` после каждой сессии

  команды, неочевидная архитектура). Порог — 200 строк; следит
  `~/Projects/claude-system/scripts/check-drift.sh`.

## Правило: пробные прогоны — только в песочнице

`extract_data.py`, `process_report.py` и `overdue_report.py` пишут результат **в текущий
каталог**: `data.json` (+ `.bak`), `telegram_priority_*.txt` / `telegram_transform_*.txt`,
`overdue_tasks_*.txt`. Поэтому любой проверочный запуск делается **на копиях**:

```bash
SP=/tmp/preview && mkdir -p $SP
cp extract_data.py process_report.py config.py data.json "ОТЧЕТ_ДД.ММ.md" $SP/
cd $SP && python3 process_report.py "ОТЧЕТ_ДД.ММ.md" --telegram-only
```

В корне проекта пайплайн запускает **владелец** — когда еженедельный отчёт полностью
собран (`./deploy.sh …`). Ассистент туда не пишет: прогон на недособранном отчёте
затрёт рабочие файлы и отправит в `⚠️ ИНФОРМАЦИЯ НЕ ПРЕДСТАВЛЕНА` проекты, статус
по которым просто ещё не внесён.

Ручное копирование заменяет локальный скилл `pipeline-preview` — он гоняет текущую
и базовую версии скриптов на одних входах и показывает diff `data.json` и
telegram-сообщений плюс проверку сходимости шт.ед.:

```bash
.claude/skills/pipeline-preview/preview.sh                 # свежий отчёт + предыдущий
.claude/skills/pipeline-preview/preview.sh --stage extract # только extract_data.py
.claude/skills/pipeline-preview/preview.sh --base HEAD~3   # сравнить с другой ревизией
```

## Архитектура

```
extract_data.py   →   data.json   →   index.html  →  js/main.js → js/* (ES-модули)
(Python-скрипт)       (данные)        (оболочка)      (точка входа)  css/styles.css
```

> **UI модульный (с Фазы 2 / D4):** `index.html` — только разметка-оболочка; стили в `css/styles.css`,
> логика в ES-модулях `js/` (точка входа `js/main.js`). Открывать по http (ES-модули требуют CORS),
> не как `file://`.

## Архив (`archive/`)

Старые датированные файлы вынесены из корня в `archive/` (в корне остаётся рабочий набор
за последнюю неделю):

| Подкаталог | Содержимое |
|-----------|-----------|
| `archive/issues/`   | старые выгрузки Redmine `issues_*.xlsx` |
| `archive/reports/`  | старые `ОТЧЕТ_*.md` (отслеживаются git) |
| `archive/telegram/` | старые `telegram_priority/transform_*.txt` |
| `archive/overdue/`  | старые `overdue_tasks_*.txt` |
| `archive/source/`   | старые штатка/высвобождение и прочие исходные xlsx |

Архивные `*.xlsx`/`*.txt` остаются вне git (глобальные правила `.gitignore`), поэтому ни
`git add .`, ни глобы автоопределения в `deploy.sh` их не цепляют. `ОТЧЕТ_*.md` отслеживаются
git и переносятся через `git mv` (история сохраняется).

## Обновление данных

> **Ежедневное обновление происходит само** — достаточно положить выгрузку Redmine
> в корень проекта, остальное делает LaunchAgent (см. «Автопрогон по свежей выгрузке»).
> Разделы ниже — про ручной запуск: он нужен для **еженедельной telegram-сводки**
> (`$2` — md-отчёт), которую автопрогон намеренно не трогает.

**Быстрый вариант** (одна команда):
```bash
./deploy.sh issues_16.06.xlsx ОТЧЕТ_10.06.md ОТЧЕТ_03.06.md
# $1 — xlsx Redmine, $2 — md-отчёт, $3 — предыдущий md для diff (необязателен),
# $4 — штатка, $5 — файл высвобождения (оба необязательны)
```
Штатка и файл высвобождения (`$4`/`$5`) по умолчанию определяются автоматически: берётся самый
свежий подходящий файл в корне по времени изменения (`ls -t` по `ШТАТКА_ДБ*.xlsx` и
`*Данные по высвобождению*.xlsx`, `shopt -s nullglob`), иначе — каноническое имя. Выбранные файлы
печатаются в лог.

Пайплайн скрипта: `extract_data.py $1 $4 $5` → `process_report.py $2 [--prev $3]` →
`overdue_report.py` → `git add data.json && git commit -- data.json` → `git push` в каждый
настроенный remote (`upstream`, `origin`); падение одного не блокирует остальные.
Скрипт останавливается, если HEAD не на `main` (пуш идёт в `main`, и «запушено» было бы
неправдой), а `pathspec` в коммите обязателен: без него в публичный репозиторий уезжает
всё, что лежит в индексе, — а рядом с автопрогоном человека, который это заметит, нет.

⚠️ **Пуш уносит ветку целиком, а не только `data.json`.** Любой локально закоммиченный
код уедет в оба GitHub-remote при следующем же прогоне — в том числе автоматическом,
по заброшенному в папку файлу. Правки, которые не должны уходить наружу, держать
незакоммиченными или в отдельной ветке.

**Вручную:**
1. Положить актуальные `.xlsx` файлы в папку проекта (в git не попадут — в `.gitignore`)
2. Запустить скрипт:
   ```bash
   python3 extract_data.py
   # или с явным именем файла Redmine:
   python3 extract_data.py "issues (1).xlsx"
   # или все три файла явно (redmine, штатка, высвобождение):
   python3 extract_data.py issues_15.06.xlsx ШТАТКА_ДБ_15.06.2026.xlsx "Проекты_Данные по высвобождению_15.06.2026.xlsx"
   ```
   Аргументы `$2` (штатка) и `$3` (файл высвобождения) опциональны; по умолчанию — канонические имена `ШТАТКА_ДБ.xlsx` / `ПРОЕКТЫ_Данные по высвобождению.xlsx`.
3. Закоммитить обновлённый `data.json`:
   ```bash
   git add data.json
   git commit -m "update data.json"
   git push
   ```

## Структура data.json

```
{
  updated_at  — дата/время генерации
  config      — год / redmine_base / hours_per_unit (из config.py, читает index.html)
  summary     — сводная статистика
  projects    — список проектов (из трекера "Паспорт проекта")
  all_tasks   — все задачи всех уровней (итеративный обход L1–Ln)
  curators    — данные по кураторам (штатка + высвобождение)
}
```

Поля проекта `projects[]` (дополнительные):
```
url            — ссылка на проект в Redmine (из xlsx высвобождения)
internal_hours — внутреннее высвобождение, часы (из xlsx)
external_hours — внешнее высвобождение, часы (из xlsx)
total_units    — высвобождение всего, шт.ед. (из xlsx)
closed_at      — дата закрытия (колонка «Закрыта» из Redmine)
defense_at     — дата защиты (колонка «Дата и время защиты» из Redmine)
```

## Логика сущностей

- **Проект** (`owner` = Ответственный, `manager` = Назначена)
- **Этап/Подзадача** (`executor` = Назначена)
- **Срочность задач**: `overdue` / `today` / `urgent` (≤5д) / `soon` (≤14д) / `ok`
- **Закрытые статусы**: `Закрыта`, `Закрыто`, `Выполнено`, `Выполнена`, `Завершена` — все приравниваются к закрытым; статус `Выполнено` исключается из счётчиков просрочки наравне с `Закрыта`
- **`computeTaskKPIs`**: использует `urgency` + `allTasks2026` (те же данные, что вкладка Задачи) для синхронизации KPI между вкладками; overdue подсчитывается через `t.urgency === 'overdue'`, а не через сравнение дат
